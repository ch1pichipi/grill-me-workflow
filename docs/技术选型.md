# 技术选型与取舍

记录"在什么场景下选择了什么方式、理由是什么、放弃了哪些替代方案"。

与 `docs/adr/` 的分工：ADR 只记录**难以逆转**的重大决策；本文档记录所有值得解释的选择，包括容易改的小决定。

---

## 1. 交付形态

### 场景：这个系统要做到什么程度

**选择**：单机可运行的演示项目。一个进程、一个浏览器页面搞定；无登录、无鉴权；管理员视图与玩家视图在同一个页面里切换。

**理由**：需求第 4 条（提前结束禁言的测试按钮）和第 5 条（切换玩家）本身就是为一个人自测设计的。引入鉴权与多实例只会延长"能跑起来"的时间，而不增加对审核逻辑的验证。

**放弃的方案**：半生产形态（管理员登录、多并发实例）。这些成本投在审核规则与惩罚逻辑上收益更高。

---

## 2. 领域语言

### 场景：需求里说的"封禁"

**选择**：正式术语定为 **禁言（Mute）**，"封禁"记为 `_Avoid_`。

**理由**：本系统的边界只到聊天。需求第 3 条的实际语义是"无法发送消息"，而"封禁/ban"在多数人认知里是账号级封停（连登录都不行）。术语一旦含糊，代码命名和 UI 文案会一路跟着含糊。

**代价**：与原始需求文档的用词不一致。以 `GLOSSARY.md` 为准。

---

## 3. 传输

### 场景：需求说"长连接服务"，但没说长连接承担什么

**选择**：WebSocket 作为唯一通道。发消息、收审核结果、收禁言生效与解除、收在线玩家消息流，全部走 WS。

**理由**：封禁的即时拦截只需要在一个地方实现一次。若聊天走 HTTP、推送走 WS，就要维护两套"是否被禁言"的判定路径，而且必然出现两者不一致的时序窗口。

**放弃的方案**：`POST /messages` + WS 推送的混合模型；WS 只做轮询替代品。需求第 4 条的"提前结束禁言"要求服务端主动推送，纯 HTTP 轮询做不到"立刻"。

---

## 4. 后端技术栈

### 场景：Windows 上要能 `go run` 起来

**选择**：`modernc.org/sqlite`（纯 Go 实现，无 CGO）。

**理由**：`mattn/go-sqlite3` 需要 CGO 与 gcc/MSVC，会把"能不能跑起来"变成环境问题。本项目的数据量（演示级）根本用不到 CGO 版的性能。

**放弃的方案**：`mattn/go-sqlite3`。

### 场景：HTTP 与 WebSocket 库

**选择**：Go 1.22 标准库 `net/http` 路由 + `github.com/coder/websocket`，不引 Web 框架。

**理由**：路由数量是个位数，标准库已经够用；框架带来的中间件生态在无鉴权、无多实例的项目里是负担。`coder/websocket` 比 `gorilla/websocket` 的 API 更小更现代。

**放弃的方案**：gin / chi / gorilla。

### 场景：代码怎么切包

**选择**：`cmd/` 作为入口，`internal/` **按能力**切成深模块（`corpus` / `moderation` / `punishment` / `store` / `httpapi`），模块内部再按自身需要分层。

**理由**：全局技术分层（`handlers/` + `services/` + `repositories/`）会让同一件事的知识摊在五个目录里，改一条规则要跳五个文件。按能力切包后，每个包对外只暴露一个窄接口（`moderation.Analyze(text) Verdict`、`punishment.Decide(severity, history) Disposition`），内部实现可以自由演进。

**附加收益**：`moderation` 和 `punishment` 是纯函数包，不碰网络与数据库，可以用表驱动测试直接钉住"等级要稳定、可解释、可审计"这条要求。

---

## 5. 前端

### 场景：Go 后端下的前端形态

**选择**：单个 `index.html` + 原生 JS，用 `go:embed` 打进同一个二进制。无构建步骤。

**理由**：演示项目最贵的成本是"怎么把它跑起来"，不是渲染性能。单二进制 + 无 node 工具链意味着任何一台机器 `go run .` 就是全部。

**代价**：语料库变更审批界面要手写。但那个界面的本质是"一列 checkbox + 可编辑 textarea"，原生 JS 足够。

**放弃的方案**：Vite + TypeScript。Go 后端本来就无法与前端共享类型，多一层构建只换来有限的类型安全。

---

## 6. 持久化

### 场景：重启后什么必须还在

**选择**：全部落 SQLite —— 语料库、语料库修订历史、玩家、消息原文、判定、禁言记录。

**理由**：需求第 6 条的价值全在"管理员辛苦用 agent 调出来的语料库"和"变更明细"上，重启丢一次，这个功能的信任就没了。禁言记录是分钟级状态，但它是判定的产物，和消息、判定存在一起才有审计价值。

**放弃的方案**：全内存；或"语料库落 JSON、其余在内存"的折中（两种存储介质、两种一致性模型，换不来多少便利）。

---

## 7. 匹配管线

### 场景：需求点名了"藏头诗嘲讽"和"火星文广告"

**选择**：`原文 → 归一化 → 视图（原始视图 / 藏头视图）→ literal（关键词）| regex（正则）`。规则多一个 `view` 字段，表示它作用于哪个视图。

**理由**：两种匹配器足以覆盖"已知字面"和"已知结构"，真正缺的能力是**在什么文本上匹配**。把"抽取"做成归一化管线上的一个阶段（视图），藏头诗就退化成"作用于藏头视图的一条普通关键词规则"——agent 只需要输出 `{view: "acrostic", pattern: "你真是个傻逼"}` 这样的普通结构，不需要会写正则；人也依然能看懂为什么被拦（系统会把抽取出来的那一列字展示出来）。

**放弃的方案**：新增第三种匹配器 `sequence`（位置序列比较）。它把"抽取"和"比较"绑成一体，规则就无法复用已有的关键词/正则机制；而视图阶段把这两件事拆开了，以后要加"取每句第 2 字""取每行首字母"只是多一个视图名，不必动匹配器。

**放弃的方案**：只做两种匹配器、不做视图。这意味着需求第 6 条点名的"藏头诗"根本无法表达（正则无法跨句取第 n 个字符），语料库就退化成一个关键词表。

---

## 8. 归一化层

### 场景：火星文/全角/形近字要不要做成代码里的常量

**选择**：归一化**映射表是语料库的一部分**，与违规规则走同一套 diff 审批流程；代码里只保留归一化的**算法**。

**理由**：需求第 6 条说"火星文格式的广告"，要拦住它改的恰恰是映射表（`嘚`→`的`、`亻尔`→`你`、全角转半角），不是违规词表。如果映射表写死在代码里、agent 改不了，agent 就只能不断生成越来越难读的正则去绕变形，语料库会退化成一堆不可解释的模式。

---

## 9. 违规等级

### 场景：一条消息命中多条规则时，等级怎么算

**选择**：等级 = 命中规则的**最高** severity（1–5）；同一条消息命中多条**不同**规则时 +1，封顶 5。规则累积命中数只作为**人工复核信号**，不参与自动处置。

**理由**：等级出现在规则、语料库、惩罚阶梯、UI 四处，它必须稳定、可解释、可审计。取最大值可以用一句话解释："这条消息里有 4 级的规则命中了"。累加则会让规则密度直接决定惩罚力度——多加几条低等级规则，同样的句子就会被自动重罚，这是刷分与规则膨胀的双重风险。

详细信息见 `docs/adr/0001-severity-is-max-not-sum.md`。

---

## 10. 违规历史的计数方式

### 场景："以往违禁情况"到底数什么

**选择**：按**违规消息条数**计数（一条消息算 1 次，与命中几条规则无关）；同时维护**滚动 7 天计数**与**终身计数**，7 天计数决定处置档位，终身计数只用于触发永久禁言。

**理由**：
- 若按"被施加禁言的次数"计数，第一次违规永远判得一样重，阶梯就失去意义。
- 若按"命中规则条数"计数，级别可以被刷：一条消息命中十条规则就等于十次违规，规则密度直接变成惩罚力度。
- 滚动窗口 + 终身计数的双计数，是因为"短期内屡犯"和"长期屡教不改"是两件不同的事，用一个数字表达不了。

### 场景：禁言期间被拦截的消息算不算一次违规

**选择**：**不计入违规历史**。

**理由**：否则一个人被禁言 1 天，期间狂刷消息就能把自己刷成永久禁言——等于让玩家自己升档，还给了恶意刷屏一个明确的收益。

---

## 11. 禁言状态机

### 场景：玩家已有一条未到期禁言，新的判定又来了

**选择**：每个玩家**最多一条活跃禁言**。新判定到来时替换为两者中更严格的一个（`max(剩余时长, 新时长)`），并在判定流里记录"被替换"这一事实。

**理由**：累加（剩余 + 新时长）会让"为什么这次禁了 4 小时"无法解释。而"禁言中再违规"在实践中几乎不会发生（入口已拦截），所以这条规则只在"管理员提前解除后立刻又违规"的边界上出现，替换语义更可解释。

### 场景：禁言到期怎么生效

**选择**：**惰性判定**（读玩家状态时比较 `now > expiresAt`）+ 在到期时刻主动推送一次"你可以说话了"。

**理由**：惰性判定没有后台定时器，也不会因为进程重启而漂移。但仅靠惰性判定意味着玩家盯着屏幕不知道什么时候能恢复——而"封禁倒计时"恰恰是测试时要看的。

---

## 12. 前端"切换玩家"

### 场景：怎么测"玩家 A 被禁言、玩家 B 仍能说话"

**选择**：单条 WS 连接切换当前身份（页面顶部玩家选择器），**另加一个管理员全局消息流面板**显示所有玩家的消息与判定。

**理由**：多开浏览器窗口才能做的对照测试，用一个全局流面板就能做完，同时还免费获得"审核实时回放"——它也正是需求第 4、6 条管理员操作的落点。

**放弃的方案**：每玩家一条独立连接（要开多个窗口才能看全）。

---

## 13. 处置档位怎么算

### 场景：severity（1–5）+ 7 天违规计数 → 禁言时长

**选择**：公式 `rung = clamp(severity + 7天计数 - 2, 0, 3)`，映射到 `[1min, 1h, 1d, 3d]`。

算出来的刻度：L1 首次 = 1min、L1 第 3 次 = 1d、L3 第 2 次 = 1d、L5 首次 = 3d。

**理由**：语义是"严重度决定起点，7 天内的第几次决定往上推几档"——这一句话能直接印在 UI 上，玩家能自己算出来下次会被禁多久，正好满足"可解释、可审计"。二维查表（5 行 × 5 列共 25 格）调起来更精细，但没有任何人能解释"为什么 L2 第 3 次是 1d 而 L3 第 2 次是 3d"；纯递进则丢掉了 severity 的全部价值。

**放弃的方案**：25 格二维表；纯递进（忽略 severity）。

---

## 14. 阶梯数据与永久禁言

### 场景：`[1min, 1h, 1d, 3d]` 放在哪，管理员能不能改

**选择**：`punishment` 包里的具名常量 + 表驱动单测锁定；前端**只读展示**当前阶梯，数据从后端读。

**理由**："管理员可配惩罚阶梯"不在需求里，加了就是白送一块 UI、一套校验、一类新的审计对象。但必须展示——不展示玩家就不知道规则；而展示数据从后端读，就不会出现"文档说 3 天、代码里 1 天"的漂移。

**放弃的方案**：阶梯入库、管理员可编辑；或干脆不展示。

### 场景：永久禁言怎么触发（阶梯四档都是有限时长）

**选择**：**终身违规计数 ≥ 5 独立触发永久**，优先级高于阶梯公式。

**理由**：语义上"永久"应该等于"屡教不改"，而不是"一次说得很脏"。若让 `rung == 3` 直接永久，则一条 5 级规则首次命中就永久禁掉一个人，而 5 级规则恰恰是 agent 最容易写宽的那一类，误报代价是一条不可逆的记录。这也让终身计数这个字段有了真实用途，否则它就是个没人读的字段。

**放弃的方案**：档位到顶即永久。

---

## 15. 7 天计数怎么读

### 场景：滚动窗口内的违规次数

**选择**：**每次现算**（`SELECT count(*) FROM judgments WHERE player = ? AND created_at > now - 7d AND is_violation`）。

**理由**：演示量级下现算毫无成本，而它保证"违规历史"只有一个事实来源——判定表。冗余计数列一旦漏加（事务回滚、进程崩溃）就会永久偏向一边，而且**不会报错**，只会让某个玩家莫名其妙被永久禁言。现算还顺带解决了"这一档是怎么算出来的"：把那条查询的结果展示给管理员看，审计就完成了。

**放弃的方案**：玩家表上冗余 `offenses_7d` 计数列 + 过期定时清理。

## 16. 需求第 6 条的"agent"是什么

### 场景：谁来提出语料库的变更

**选择**：**真实 LLM**（key 从环境变量读）。agent 输出结构化变更草案，管理员逐条勾选、可编辑、再提交。**无 key 时按钮禁用并提示"手动编辑语料库"**，系统其余部分完全可用。

三条硬约束：
1. **agent 永远不直接写库**，只产出草案（draft）。
2. **草案必须通过服务端校验**：severity 必填且在 1–5、正则必须编译通过、映射不得为空、id 不得冲突。校验失败的条目在 diff 里标红且不可提交。
3. **提交即一次修订（revision）**：记录 agent 的原始建议、管理员实际提交的差异、操作时间。

**理由**：这个能力的价值恰恰在于 agent 能提出人没想到的表达（新火星文变形、新藏头套路）。本地确定性生成器（分词 + 词表 + 模板）能做到的事，管理员手写也能做到，那就不需要 agent——它只会变成一个更慢的关键词输入框。

**放弃的方案**：本地确定性生成器；或两者都做、默认本地（等于默认不使用这个功能）。

---

## 17. 一条判定要留多少东西

### 场景：语料库会被改，历史判定不能跟着变

**选择**：消息原文（截断 2000 字）+ 归一化后文本 + 命中规则的**快照**（规则 id、当时的 severity、当时的模式文本、当时的视图）。

**理由**：只存规则 id 有个隐藏的坑——管理员把一条规则的 severity 从 2 改成 5，历史上所有旧判定会**追溯变重**；而阶梯是根据历史现算的，历史判定的 severity 一漂，永久禁言的门槛就跟着漂。存快照之后，"当时判得多重"和"现在规则是什么"是两件独立的事实。

**放弃的方案**：只存规则 id（severity 从当前语料库读）；只存最终处置。

---

## 18. 规则的结构，以及"句"怎么切

### 场景：一条规则有哪些字段

**选择**：`id / 说明 / view(raw|acrostic) / matcher(literal|regex) / pattern / severity(1–5) / enabled / examples`。

**理由**：`examples` 让每条规则**自带可执行的证据**——提交时服务端拿它反向验证"这条规则真的能命中它自己声称的样例"。agent 编造一条"看起来很对但永远不命中"的规则会被当场抓住，这是把"精准度"变成可验证的第一道闸。

### 场景：藏头视图里什么算"一句"

**选择**：按**换行 + 中文标点**（。！？；，、……）切分，取每段第一个非空白字符。

**理由**：只按换行切会漏掉"一行里连着说三句"的藏头——玩家很自然会这么发（`你真傻。今天天气不错。`）。拆成两个视图（`acrostic-line` / `acrostic-sentence`）则让管理员和 agent 都要为每条规则多做一个不常需要的选择。

**放弃的方案**：只按换行切；两个视图并存。

---

## 19. 归一化映射的结构与应用顺序

### 场景：`亻尔 → 你` 和 `尔 → 你` 同时存在

**选择**：映射是 `{id, from, to, note}` 的**有序**列表，按 `from` 长度降序应用，等长按 id。

**理由**：若先应用 `尔 → 你`，`亻尔` 会被拆成 `亻你`，那条映射就永远不生效——而且**不会报错**，只表现为"这条映射莫名其妙没用"。长度降序是这条管线的核心不变量，写死并单测。

**放弃的方案**：无序集合（顺序不确定）；允许正则替换（给 agent 无限表达力，却让"这条映射改了什么"不可读，顺序敏感的正则级联极难调试）。

---

## 20. 变更草案的形态

### 场景：agent 提出十条变更，其中两条有问题

**选择**：结构化操作列表 `[{op: add|update|delete, target: rule|mapping, before, after, reason}]`；管理员逐条勾选、逐条编辑 `after`，**允许只提交勾选的子集**。校验失败的操作标红且不可勾选，其余照常提交。

**理由**：每条操作都要被**单独校验**（severity 范围、正则能编译、examples 能命中、id 不冲突、映射非空）。文本 diff 拿不到操作边界，只能整体校验，一条坏 regex 会挡住另外九条好的。"全有或全无"则是为了让两条废建议，丢掉八条有用的。

**放弃的方案**：整份语料库的文本 diff；结构化操作但必须全有或全无。

---

## 21. 修订的存储与回滚

### 场景：要不要能退回旧版语料库

**选择**：每次提交存**本次操作列表 + 提交后的完整语料库快照**（JSON）。回滚 = 把某个历史快照**作为一次新的修订**提交，不删除历史。

**理由**：语料库是几百条量级，整份快照几十 KB，存两份的成本可忽略。反向应用操作是这类系统最经典的翻车点（删掉的规则 id 被后来的 add 复用，反向 delete 就删错了对象）。回滚作为新修订，则"谁在什么时候把语料库退回到哪个版本"本身也可审计。

**放弃的方案**：只存事件流（回滚靠反向应用）；只存快照（则需求第 6 条的"变更明细"丢失，agent 建议与人工修改无法对照）。

---

## 22. 匹配时规则从哪读

### 场景：需求第 3 条写的是"高速字符串匹配"

**选择**：进程内**内存快照**——`atomic.Pointer` 持有当前语料库的编译产物（关键词索引 + 已编译正则）；提交修订后重建并原子替换。

**理由**：每条消息要跑的关键词可能几百条，每条一次 SQL 往返就把"高速"否掉了。原子替换还保证了"提交那一刻之后的消息按新语料库判"，既没有定期重载的窗口期，也不会出现"匹配到一半语料库被换了"的撕裂。

**放弃的方案**：每条消息查一次 SQLite；定期（每 N 秒）重载。

---

## 23. agent 的输入边界

### 场景：agent 只看到语料库和管理员那句话够不够

**选择**：默认只给**当前语料库 + 管理员指令**；前端提供"附带最近消息样本"的勾选项，勾上后才把最近 N 条消息与判定（**演示项目自己造的数据**）一起给 agent。

**理由**：不给样本时 agent 只能凭想象发明规则，写出的正则会过度拟合它想象的攻击方式；给了样本它才能说出"最近 20 条里有 3 条是 `。/` 分割的卖片广告，现有规则全没拦到"这种可验证的话。默认不带，是因为真实聊天记录不该进 prompt——这条约束在演示项目里就要立住。

**放弃的方案**：无条件附带消息历史；再附带"被拒绝过的历史草案"（拒绝理由没有结构化记录，喂给模型只会引入歧义）。

---

## 24. 怎么验证"语料库改完更准了"

### 场景：需求第 6 条的目标是"提高审核精准度"，改完没有手段证明

**选择**：**试跑面板**——粘贴一段文本（或从历史消息里选），用**当前草稿状态**的语料库跑一遍，显示命中规则、severity、档位、会施加的禁言时长；不写库、不产生判定。

**理由**：它把"提高精准度"变成提交前就能看着数字判断的动作，能当场发现"这条新规则会误伤正常聊天"。实现上只是复用 `moderation.Analyze` + `punishment.Decide` 两个纯函数——这是按能力切包的直接回报。

**放弃的方案**：不加，靠实际发消息试；只能跑提交后的语料库（发现问题时已经改完了）。

---

## 25. 玩家从哪来

### 场景：切换玩家的下拉框里有什么

**选择**：**管理员可增删玩家**（玩家是一等实体），下拉框列出当前存在的玩家。

**理由**：玩家成为显式实体之后，测试可以复现——同一份玩家名单、同一个玩家名，每次跑出来的历史与档位都可对得上；而"首次发言自动建档"会让名单随测试过程漂移，同一个名字可能指向不同历史。它也给了管理员一个自然入口去看某个玩家的历史与当前禁言。

**代价**：必须处理"删除一个已有违规历史的玩家"这一语义（见下节待确认）。

**放弃的方案**：预置固定名单（不够测）；首次发言自动建档（名单漂移，历史不可复现）。

### 场景：删除一个有违规历史的玩家

**选择**：**软删除**。标记为已删除，从玩家列表与切换框消失，消息、判定、禁言全部保留；同名可重建为一个新玩家。

**理由**：硬删除 + 级联会毁掉审计链——一个被永久禁言的人要解释"凭什么"，而他的三次违规判定已经被删掉了。硬删除但保留判定，则会在"查这个玩家历史"的每个地方制造空指针，而这类代码最难测。软删除的代价只是每张表多一个 `deleted_at`，以及玩家名唯一性只在未删除范围内成立。

**放弃的方案**：硬删除 + 级联；硬删除 + 保留孤儿判定。

---

## 26. SQLite 的 schema 怎么管

### 场景：表结构还会被推翻重写

**选择**：单文件 `schema.sql`，启动时执行 `CREATE TABLE IF NOT EXISTS`，**不做迁移**。

**理由**：演示项目的 schema 大概率会被整体推翻重写，这时候迁移脚本是纯负担——你会写一堆只服务于"已经被丢弃的表"的脚本。等真出现"线上数据不能丢"的需求，再加迁移。

**放弃的方案**：goose / golang-migrate。

---

## 27. 测试写到什么程度

### 场景：哪些逻辑值得被测试钉住

**选择**：`moderation`、`punishment`、语料库校验做**表驱动测试**；再加**一条端到端冒烟测试**（起进程 → 连 WS → 发一条违规消息 → 断言收到禁言事件与到期时间）。

**理由**：纯函数测试负责"判得对不对"，一条端到端冒烟负责"接口接没接错"——后者是唯一能抓住"两个包各自都对、但组装起来错了"的测试。每个 WS 事件都写集成测试则会在演示项目里迅速变成维护负担，改一个字段名要改十处测试。

**放弃的方案**：只测纯函数（频道接线无人验证）；全链路集成测试。

---

## 28. LLM 怎么接

### 场景：只有一个 provider

**选择**：一个 `Drafter` 接口 + 一个真实实现（默认走 OpenAI 兼容中转站 `opencode-go`：`https://opencode.ai/zen/go/v1`，模型 `deepseek-v4.1-flash`，key 读 `AGENT_API_KEY`，出厂带默认值，可用 `AGENT_BASE_URL` / `AGENT_MODEL` 覆盖，显式置空 key 即禁用）+ 一个 fake 实现供测试。

**理由**：接口留好了，换 provider 是加一个实现的事。现在就做多 provider 抽象，等于用"还不存在的第二个 provider"去猜抽象的形状，通常猜错。

**放弃的方案**：多 provider 抽象 / 配置化模型列表。

---

## 29. 给 agent 的样本

### 场景：勾选"附带最近消息样本"时给它什么

**选择**：最近 30 条消息 + 各自的判定结论（命中规则、等级、处置），并在草案里标注"这条建议基于哪几条样本"。

**理由**：只给消息文本不给判定，agent 就不知道哪些已经被拦住了，会郑重提议一条其实已经生效的规则。

**放弃的方案**：只给消息文本；给全量历史（prompt 成本与噪声都不划算）。

---

## 30. 需求文档的术语

### 场景：`初步需求文档.md` 里写的是"封禁"

**选择**：把其中的"封禁"改为"禁言"，并在文档开头加一行"术语以 `GLOSSARY.md` 为准"。

**理由**：这份文档是这个项目唯一的原始输入，几个月后最先被读到的就是它——不改，就会有人照着它写出 `banPlayer` 这种命名，而系统里根本没有"ban"这个概念。

**放弃的方案**：把它当作不再变动的历史输入、只在 `GLOSSARY.md` 里定名。表面更"干净"，实际是把歧义留在了最显眼的位置。

---

## 31. 玩家用什么当身份

### 场景：软删除后同名重建

**选择**：**内部自增 id + 名字字段**。前端显示名字、按 id 切换，名字可改。

**理由**：拿名字当 id 与软删除直接冲突——软删除后同名重建，名字就不再唯一。UUID 在本项目唯一的收益是跨实例不撞，而我们永远只有一个实例。

**放弃的方案**：名字即 id；UUID。

---

## 32. "提前解除"记录什么

### 场景：没有鉴权，也就没有操作人

**选择**：记录**原因（必填）** 与时间，操作人固定为 `admin`；并据此修正 `GLOSSARY.md` 中"留下操作人与原因"的描述。

**理由**：为了拿一句文档描述成立而引入鉴权，是本末倒置。而"原因必填"是真正有价值的那部分——它会出现在判定流里，测试时能直接回看"这次为什么提前放了"。

**放弃的方案**：补一个共享口令的极简管理员身份。

---

## 33. 玩家列表显示什么

### 场景：测试时要能算出"下一次会判多久"

**选择**：名字 + 当前禁言状态（含剩余时间）+ 7 天违规次数 + 终身违规次数。

**理由**：这四个数字正好是档位公式的全部输入。摆在一起，你可以一眼算出下一次的时长，不用翻日志。

**放弃的方案**：只显示名字。
