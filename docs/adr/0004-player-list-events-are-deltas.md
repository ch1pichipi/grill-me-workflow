# 玩家列表事件是增量，且非发送者的计数允许陈旧

一条消息只广播**变动的那一行**（`players.changed`，客户端按 id 合并）。整份 `players` 只在三处出现：连接建立时的 `bootstrap`、建/改/删玩家（100ms 合并后广播）、以及客户端重连。代价是：一个不发言的玩家，其列表行上的 7 天计数可能停在旧值，直到他下一次发言或页面重连。

之前的做法是每条消息都重算并广播整份玩家列表。`playersLocked` 对每个玩家跑 3 条 SQL（活跃禁言 + 7 天计数 + 终身计数），于是每条消息在全局锁内产生 `3N+1` 条查询，并向每个连接推一份 `N` 行的 JSON（500 玩家约 91KB）。这是 `O(玩家数 × 消息数)` 的活，全部发生在同一把锁里——玩家越多，每个人发消息越慢，而慢下来的原因与他自己无关。

关键在于**这活本来不必干**：`Send` 在判定过程中已经算出了发送者自己的禁言、7 天计数、终身计数（它们恰好是档位公式的全部输入）。也就是说，消息热路径上唯一需要的玩家数据，在进入广播那一刻已经在手上，零额外查询。

**允许陈旧的边界在哪里。** 7 天计数会随时间自然衰减（7 天前的违规滑出窗口），所以非发送者的显示值只可能**偏高**，不会偏低；而真正进入处置决策的数字永远是 `Send` 里对单个玩家的现算值（`docs/技术选型.md` §15 未变）。界面上的两个计数是**展示**，不是决策输入——这条区分是接受这个取舍的前提。

**为什么删掉全量广播不会让状态失准。** 到期这件事有两条路送达：`scheduleLocked` 的主动定时器，以及 `muteEvent`；`playersLocked` 里的惰性写回只兜住"进程停摆期间到期"这类边界。更根本的是，客户端错过事件的兜底机制本来就不是全量广播，而是 `enqueueBroadcast` 在队列积压时**断开连接**（`ws.go`），重连后由 `bootstrap` 拿全量。增量把这套自愈机制的价值放大了：丢一条增量只影响一行，而断线重连会拿到整份最新状态。

**锁定"成本与玩家数无关"这条不变量。** 光靠代码审视守不住它——下一个人加一行 `s.broadcastPlayersLocked()` 就悄悄回来了。所以：`store` 有一个仅供测试的玩家状态读查询计数器，单测断言玩家数从 1 涨到 50 时，一条消息的查询条数与广播字节数都不变；压测脚本另外打印"每消息玩家状态流量/连接"，两档玩家数对比。

**不要**把全量广播改成"每 N 条消息或每 N 毫秒补发一次整份列表"来修这个 bug：它把 `O(N)` 的成本从"每条消息"降到"每个窗口"，但仍然是 `O(N)`，而且引入了"补发的全量可能覆盖掉刚到的增量"这个乱序问题。合并器只服务于建/删玩家这类低频、改动集合本身的操作，且**必须仍在锁内广播**，才能保住"事件顺序 == 状态顺序"。

**不要**为了省掉那 4 条批量查询而在玩家表上加冗余计数列（`docs/技术选型.md` §15 已否决）：漏加一次不会报错，只会让某个玩家莫名其妙被永久禁言。
